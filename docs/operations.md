# 開発者・運用マニュアル

ドッグフーディング（実機での長期稼働テスト）中の運用手順書。
「PCを再起動した」「スマホからAIが動かない」ときに、ここだけ見れば復帰できることを目指す。

仕様そのものは `docs/app-specification.md`、決定の経緯と不採用一覧は `docs/user-context.md` を見ること。

---

## 1. 全体構成

EvJou の AI 機能（`proxy` モード＝「EvJou AI」）は、スマホから自宅PCへ**バケツリレー**で届く。

```
スマホ (EvJou APK)
   │  ① ai_requests に status:"pending" で文書を書く
   ▼
Firestore (evjou-efd9b)          ← クラウド。常時稼働
   │  ② pending を監視しているワーカーが拾う
   ▼
proxy/index.js (自宅PCで手動起動) ← ★落ちていると全部止まる
   │  ③ localhost:11434 へ推論を投げる
   ▼
Ollama (自宅PCの常駐アプリ)       ← ★落ちていると全部止まる
   │  ④ 結果を文書に書き戻す（status:"completed"）
   ▼
スマホ（onSnapshot で受信）
```

**★の2つは自宅PCで動いている必要がある。** どちらかが落ちていればスマホ側は
「AIサーバーがメンテナンス中です」で止まる。**日記・ToDo・ルーチンはローカル保存なので、
AIが落ちていても通常どおり使える**（そういう設計にしてある）。

AI以外の機能は一切ネットワークを使わない。ワーカーの停止＝AIだけが止まる、と覚えておけばよい。

## 2. PC再起動後の起動手順

順番に実行する。所要 1〜2分。

### ① Ollama が動いているか確認

Ollama は Windows サービスではなく**常駐アプリ**なので、スタートアップから外れていると上がらない。

```powershell
netstat -ano | Select-String ":11434"
```

`LISTENING` の行が出れば OK。出なければスタートメニューから **Ollama** を起動する。

モデルまで確認したいとき:

```powershell
(Invoke-RestMethod http://localhost:11434/api/tags).models | ForEach-Object { $_.name }
```

`qwen2.5:7b` が一覧にあること（ワーカーの既定モデル）。

### ② ワーカーが二重に起動していないか確認

**これが一番やりがちな事故。** 前のプロセスが残ったまま2本目を起動すると、両方が同じ文書を
処理して推論と利用回数が二重に走る。起動前に必ず確認すること。

```powershell
Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object { $_.CommandLine -like '* index.js' } | ForEach-Object { $p = Get-Process -Id $_.ProcessId; "PID $($_.ProcessId)  起動 $($p.StartTime)" }
```

- **何も出ない** → そのまま ③ へ
- **1件以上出る** → 既に動いている。作り直すなら §3 で止めてから ③

### ③ ワーカーを起動

専用のターミナルを1枚開き、**フォアグラウンドで**起動する。ログがそのまま流れるので、
実機テスト中はこの窓を開いたままにしておくのが一番わかりやすい。

```powershell
cd E:\!master_0428\Document\Claude\Evjou\proxy
node index.js
```

正常なら3行出て待機に入る:

```
✅ Firebase Admin SDK initialized.
👀 Firestore `ai_requests` コレクションの監視を開始します...
```

（`♻️ 孤児リクエストを復帰: N件` が挟まることがある。前回の異常終了で処理中のまま残った
文書を拾い直しただけなので正常。）

### ④ 疎通確認

スマホの EvJou でAIを1回叩く。ワーカーのターミナルに以下が流れれば全経路OK。

```
処理開始: ReqID=..., User=...
✅ 処理完了: ReqID=... (本日 N/50 回)
```

## 3. 停止・再起動

**停止（フォアグラウンドで起動した場合）**：そのターミナルで `Ctrl+C`。

**停止（窓を閉じてしまった／バックグラウンドに残っている場合）**：

```powershell
Get-CimInstance Win32_Process -Filter "Name='node.exe'" | Where-Object { $_.CommandLine -like '* index.js' } | ForEach-Object { Stop-Process -Id $_.ProcessId -Force; "stopped $($_.ProcessId)" }
```

> `* index.js` という末尾一致にしてあるのは、StreamDeck プラグインや他の Node アプリを
> 巻き込んで殺さないため。条件を緩めないこと。

**再起動**：上で止めてから §2③ を実行する。ワーカーは起動時に非終端ステータス
（`queued` / `processing` / `waiting_for_server`）の文書を `pending` へ戻すので、
**再起動しても処理中だったリクエストは自動で拾い直される。** 手作業でのFirestore掃除は不要。

## 4. 設定値

### ワーカー側（`proxy/.env` で上書き可。未設定なら既定値）

| 変数 | 既定値 | 意味 |
|---|---|---|
| `OLLAMA_URL` | `http://localhost:11434/v1/chat/completions` | 推論先 |
| `OLLAMA_MODEL` | `qwen2.5:7b` | 使用モデル |
| `OLLAMA_TIMEOUT_MS` | `120000` (2分) | 1回の推論の上限。ハングでキュー全体が止まるのを防ぐ |
| `DAILY_LIMIT` | `50` | 1日の利用上限。**課金対策ではなく暴走・無限ループ対策の安全弁** |
| `KEEP_HOURS` | `24` | 処理済み文書の保持時間。30分ごとに古いものを削除 |

リトライは Ollama 側の失敗に対して**5回・5秒間隔**（コード内固定）。

### アプリ側（`src/api/client.js` の締切。コード内固定）

| 定数 | 値 | 意味 |
|---|---|---|
| `PROXY_ACK_MS` | 60秒 | この間に受理されなければ**ワーカー不在**と判定 |
| `PROXY_PROGRESS_MS` | 180秒 | 受理後、文書の更新が途絶えたら打ち切り |
| `PROXY_MAX_MS` | 600秒 | 何があってもこれ以上は待たない絶対上限 |

締切を「経過時間」ではなく「**進捗が途絶えた時間**」で測っているのがポイント。
ワーカーは生きている限り `queuePosition` を更新し続けるので、
「順番待ちで長い」と「PCが落ちている」を区別できる。

**混雑時の注意**：順番待ちが長引いても、文書が更新され続けている限り 600秒までは待つ。
600秒を超えると待ち順に関係なく打ち切られる。

## 5. 既知の問題と回避方法

**いずれも通常の利用フローでは踏まない。実機テストの阻害にはならないと判断して未修正。**
踏んだら記録して、v1リリース前に直す。

### 5-1. ボタン連打で更新を取りこぼす可能性がある

**対象**：ToDoのチェック / 削除 / 期限変更 / テキスト編集（`src/features/useTodos.js`）

**内容**：これらは関数アップデータではなくクロージャが捕まえた `todos` を見ている。
同一の描画サイクル内に2回以上の更新が入ると、後の更新が前の更新を上書きして
**1回目の操作が消える**。

**踏む条件**：同じ瞬間（1フレーム内）に2操作。人間の指では通常起こらない。

**回避**：**1つ操作したら画面に反映されたのを見てから次を押す。** 連打しない。

**踏んだときの症状**：チェックしたはずのToDoが外れたまま／消したはずのToDoが残る。
データは壊れない（保存されなかっただけ）ので、もう一度操作すれば直る。

### 5-2. 過去の日付を開いた状態の「🔥 今日へ」は今日にならない

**対象**：AI提案タスクの仕分けボタン（`src/daily-journal.jsx` の `fileProposal`）

**内容**：追加されるToDoの期限に「**今日**」ではなく「**画面で選択中の日付**」が入る。
日付セレクタで昨日以前を開いたままAI提案を仕分けると、その過去日が期限になり、
稼働シーケンスの「🔥 今日」ではなく「**⏮ 昨日までの未完了（繰り越し）**」に入る。
ボタンのラベルと実際の挙動が食い違っている。

**踏む条件**：過去の日付を開いた状態でダンプ整理／日記保存を行い、出てきた提案を仕分ける。
今日の日付を開いていれば正しく動く（通常の使い方）。

**回避**：**AI提案を仕分ける前に、日付セレクタを今日に戻す。**

**踏んだときの復旧**：ToDoタブでそのタスクの期限を今日に付け替えれば直る。データ破損ではない。

### 5-3. ワーカーは自動で復活しない

detached プロセスなので、**PCのスリープ・再起動・シャットダウンで落ちる。**
自動起動も自動再起動も設定していない。PCを再起動したら §2 を手で実行すること。

スマホ側からは「AIサーバーがメンテナンス中です」としか見えないので、
**AIが効かないと感じたら、まずPC側でワーカーが生きているかを見る**（§2②）。

### 5-4. 初回のAI利用で同意ダイアログが出る

端末ごとに1回だけ「EvJou AIを利用すると、日記の内容が開発者のサーバーに送信されます」
という確認が出る。同意しないとAIは動かない。アプリのデータを消して入れ直すと再度出る。

> **記載の正確性について**：このダイアログは「サーバー上にデータは保存されません」と表示するが、
> 実際にはリクエスト文書（日記本文を含む）が Firestore 上に **処理後最大24時間**（`KEEP_HOURS`）
> 残ってから削除される。自分専用のうちは実害がないが、**他人に配布する前に文言を直すか
> `KEEP_HOURS` を短くすること。** v1リリース前の宿題。

## 6. トラブルシューティング

スマホ側のエラー文言から原因を引く。

| スマホの表示 | 原因 | 対処 |
|---|---|---|
| AIサーバーがメンテナンス中です | 60秒以内に受理されず＝**ワーカー不在**。またはワーカーは生きているが Ollama が落ちている | §2① と §2② を順に確認。落ちていれば §2③ で起動 |
| AI利用制限に達しました | その日の利用が `DAILY_LIMIT`（50回）に到達 | 翌日まで待つ。テストで意図的に使い切ったなら `proxy/.env` の `DAILY_LIMIT` を上げて**ワーカー再起動** |
| （反応が無いまま10分で打ち切り） | 推論が終わらない。モデルが重い／GPUが詰まっている | ワーカーのログを見る。`⏳ Ollamaリトライ待機中` が並んでいれば Ollama 側の問題 |
| 通信エラー。インターネット接続を確認してください | スマホが Firestore に到達できていない | スマホの回線を確認。PC側は無関係 |

ワーカー側のログから引く。

| ログ | 意味 | 対処 |
|---|---|---|
| `❌ serviceAccountKey.json が見つかりません` | 起動できない。鍵ファイルが無い | `proxy/serviceAccountKey.json` を置く（**Gitには入っていない**。§8参照） |
| `♻️ 孤児リクエストを復帰: N件` | 前回の異常終了ぶんを拾い直した | 正常。対処不要 |
| `⏭ 他のワーカーが取得済み` | **ワーカーが二重起動している** | §3 で全部止めて1本だけ起動し直す |
| `⏭ キャンセル済みのためスキップ` | 順番待ちの間にスマホ側が諦めた | 正常。対処不要 |
| `⚠️ 未処理のPromise拒否（稼働は継続）` | 想定外の例外を握り潰した | 稼働は続くが**バグの兆候**。ログを控えて報告 |
| `監視エラー` | Firestore への接続が切れた | PCのネットワークを確認。復帰しなければワーカー再起動 |

**症状が「AIだけ動かない」なら、日記・ToDoは平常どおり使える。** テストを止める必要はない。

## 7. コードを触るときのルール

```bash
npm run build            # 本番ビルド。リファクタ後は必ず通す
npm run test:dataloss    # 手入力消失対策の実機ブラウザ回帰テスト（生命線）
```

- **`src/features/useJournal.js`（ジャーナルの保存経路）を触ったら `test:dataloss` を必ず通す。**
  自動保存(800ms) / 日付切替フラッシュ / リロード保険(beforeunload) / レガシー移行の4件が
  すべて PASS すること。
- 大きな一括書き換えは過去にパーサエラーを起こしている。**小さく変えて都度ビルド検証**する。
- 日付は必ず `toLocalDateStr()` を使う。`toISOString()`（UTC）は使わない。
- `proxy/index.js` を触ったら、ワーカーを再起動してから疎通確認（§2④）まで通す。

## 8. Git に入っていないファイル（＝新しいPCでは手当てが必要）

このリポジトリは **public**。秘密情報は一切コミットしていないので、
クローンしただけでは以下が欠けている。

| ファイル | 用途 | 無いとどうなる |
|---|---|---|
| `proxy/serviceAccountKey.json` | Firebase Admin の秘密鍵 | ワーカーが起動しない |
| `android/keystore.properties` | リリース署名のパスワード類 | 署名済みAPKが作れない（デバッグビルドは通る） |
| `android/app/evjou.keystore` | リリース署名の秘密鍵 | 同上 |

`android/keystore.properties` の書式（**値は各自の控えから入れる。ここには書かない**）:

```properties
storeFile=evjou.keystore
storePassword=＜控えを参照＞
keyAlias=evjou
keyPassword=＜控えを参照＞
```

> ### ⚠️ evjou.keystore は絶対に失わないこと
> Androidは「同じ署名鍵で署名されたAPKだけ」をアップデートとして受け付ける。
> **鍵を失うと、既存インストールへのアップデート経路が永久に切れる**（ユーザーは
> 一度アンインストールしないと新版を入れられない）。再生成では代用できない。
>
> 同時に、**鍵を漏らしてもいけない**。公開されると誰でも同一署名のAPKを作れる＝
> アップデートのなりすましが可能になる。こちらも回収不能。
>
> **リポジトリの外**（USBメモリ・パスワードマネージャ等）に必ずバックアップを取ること。
> `.gitignore` で `android/app/*.keystore` と `android/keystore.properties` を除外済み。

## 9. データの保存場所とバックアップ

| 環境 | 保存先 |
|---|---|
| Androidアプリ | IndexedDB ＋ Capacitor Preferences への二重書き（WebView消去対策）。読み出しは IndexedDB → Preferences → localStorage の順にフォールバック |
| ブラウザ | IndexedDB（旧データは localStorage から自動移行） |

**日記・ToDo・ルーチンはすべて端末内。クラウドには同期していない。**
（Firestore を使うのはAIリクエストの受け渡しだけで、そちらは24時間で消える。）

つまり**端末を初期化するとデータは消える。** 設定画面のエクスポート機能で
定期的にJSONを吐いておくこと。ドッグフーディング中は特に、
節目でエクスポートしておくと安心。

保持件数の上限（設定画面で変更可）:

| 対象 | 既定 |
|---|---|
| 日記 | 730日 |
| 完了ToDo | 100件 |
| ルーチンのチェック履歴 | 365日 |

上限を超えた古いものから自動で削除される。長期テストで消えて困るものは
上限に達する前にエクスポートしておく。
